## 过程：一次 FAIL，以及修复

ADR-0108 整合后，第一次正式矩阵跑在 `main@4e78e255`，结果为 **FAIL**（证据级），原始数据见 `artifacts/e1-cap1-main-4e78e255-k0-fail.json`：

| stage | 10k | 100k | 500k | growth |
|---|---|---|---|---|
| write_crash | 50.0 / 53.4 / 58.4 | 126.8 / 127.7 / 129.7 | 273.5 / 276.0 / 280.4 | **230.4** |
| resume | 63.5 / 65.9 / 67.1 | 159.9 / 160.6 / 163.7 | 294.7 / 299.7 / 304.7 | **241.2** |
| replay | 52.9 / 52.9 / 53.4 | 148.7 / 152.8 / 153.1 | 309.4 / 320.9 / 325.9 | **273.0** |
| read_batch | 36.3 / 37.0 / 41.1 | 43.0 / 44.3 / 45.8 | 72.5 / 73.8 / 80.5 | **44.2** |
| metadata | 1.5 | 1.5 | 1.5 | 0.0 |

诊断与定位：

1. 用 2k / 5k / 100k、单次重复的诊断运行做 bisect，跳变出现在 `ccfe840`（Raw 归档元素一个单元一个 snapshot）。此前的 `6be9a44` 在 100k 下 replay 为 48 MiB，从 `ccfe840` 起约 125–150 MiB。
2. 进程内每 20 ms 采样 VmRSS 与主线程栈，发现增长集中在对整单元的有界扫描上：Raw `_spool_unit`、Canonical `_spool_block`、校验器的单元复核。这些扫描单独运行就能复现：100k 单元裸扫描 +82 / +99 MiB，同样 batch 下 5k 单元只有 +13 / +16 MiB。
3. 排除的原因：memray 记录的堆峰值约 65 MB；`malloc_trim` 没有效果；SQLite 缓存上限为 1 MiB；`UnitFingerprint` 落盘 spool，测得 RSS 平坦；把 row group 缩到 1024 / 256、scan batch 缩到 1024 / 4096、`use_threads=False`，都只部分改善或没有改善。
4. 根因：暂存写入器把整个单元写成一个 Parquet 文件（`UNIT_FILE_ROWS = 4 194 304`，每个 row group 8192 行）。Arrow 对单个文件的 fragment 扫描，内存随该文件的 row group 数增长，所以每次对单元的有界扫描都变成 O(单元)。ADR-0108 之前，文件规模由 D2 / 微批限定（4096 / 256 行）。
5. 修复（`bfe7aea5`，经 PR #24 合入，`main@25ffada5`）：单元数据文件上限为一个 4096 行的 row group。这与 ADR-0108 之前 D2 元素批文件的规模相同。单元仍然只有一个 snapshot（ADR-0108 §1）；指纹按行计算，与文件切分无关。修复后的诊断（100k）：write_crash 126 → 54、resume 159 → 61、replay 148 → 51 MiB，ADR-0108 之前的基线为 60 / 62 / 48。另补结构测试 `test_a_committed_unit_is_spread_over_bounded_one_row_group_files`。
6. 同期还修复了探针预填充：2025-01-01 之前的日期按毫秒 tick 生成（`815b6ee3`）。修复前，K = 1000 在第 152 个单元被严格解析器拒绝。

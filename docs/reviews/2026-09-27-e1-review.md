## 阻断项 E1-CAP-1：单元级 O(N) 状态违反 G3-S 容量目标

`normalizer.py` 的窗口证明和写入确实逐批处理完整 Raw 行，但复核发现除了初审中的位置与完整性数组外，严格证明路径还保留归档解析结果和随批次数增长的计划 / 提交状态：

1. `_positions()` 对整单元执行 `scan_columns(position, symbol)`，把全部位置 `to_pylist()` 后排序；`_survey()` / `_unit_facts()` 将其作为完整 tuple 保留。
2. `_committed_times()` 一次读取整单元全部 `arrival_seq` 与 `knowledge_time`。
3. `_survey()`、`_unit_facts()` 和 `_close()` 构造包含全单元序号的 Python list，并逐行比较；完整 `verify_unit()` 还会保留所有已规范化行。
4. `PersistedRowVerifier(cache_archives=True)` 缓存已解析归档的 `pa.Table`，后续 `_verify_archive_rows()` 再从整张表 `.take()`。因此即使 normalizer 的 Raw 扫描改成窗口，D1 严格归档证明仍会把与单元大小成比例的数据留在内存。
5. `_CommittedPlan.batches`、排序后的 batch index、`_write()` 的 `done` 映射与提交列表 / 元组都随 `N / M`（总行数 / microbatch 行数）增长；仅把每批 row payload 变小，不会令长期驻留元数据有界。
6. Claude 在独立分支 `fix/e1-cap1` 提交的初版（`2f98cd2`, `97772ba`，尚未集成）已压缩部分位置状态并加结构测试，但还没有满足上述全路径边界。新增测试的 collector 未递归审计深层缓存容器；N=10/70、M=10 只有 1/7 个批次，汇总最大值会掩盖按 batch 数增长的集合。不得据此接受 E1-CAP-1。

因此“Canonical 完整行按 microbatch 处理”成立，但“严格 normalizer 证明 / 提交路径的内存只随固定工作窗口增长，而不随 N 或批次数增长”不成立。既有测试只限制宽行窗口；此前结构测试会过滤 `width > 3` 扫描，未约束窄列批量 materialize、Python 集合、缓存的完整 archive table 或随批次数增长的状态。探针也尚不能作为证据：`ru_maxrss` 是进程历史 high-water，不能直接以测前当前 RSS 相减来归因阶段峰值；Arrow pool peak 同样可能包含前序分配。此结论来自代码审查与测试断言，不是生产规模外推。

该项与 ADR-0028 的语义要求分开：目前没有发现足以证明 lineage、批次恢复或 Canonical 行映射错误的反例；但是 E1 的 G3-S 容量验收目标属于该批次范围，故不能只接受正确性部分并把容量需求降格为“以后再测”。

## 后续关闭标准

Claude 应在不放宽 ADR-0028 的完整性语义下，改造完整的严格证明与规范化路径；容量边界必须覆盖 Raw 扫描、D1 归档验证、规划、续跑、提交核验和 API 返回对象。工作集可以依赖明确配置的 microbatch / 固定缓冲区，加固定常数开销；不能随 N 或 `ceil(N/M)` 批次数增长。必须特别消除（或以有界磁盘 spool / 可重复有界扫描替换）完整 `ParsedArchive.rows` 缓存和 Python 持有的 batch-plan / done / commit 列表。基础设施层 `scan_columns().to_arrow()` 会整读返回结果；任何全量窄列证明也必须分页 / 范围化或新增真正批处理 reader，不能只把列宽缩小。不得修改冻结的 `core/` 契约。可以保留明确命名的全量便利 API（例如有意收集整单元行的调试 / 导出方法），但它必须与生产 bounded path 清楚隔离，不能由 normalizer 的默认证明 / 写入路径隐式调用。

实现需保持固定 snapshot、一次 clock、精确逐批 fingerprint / readback、缺行 / 重复 position 检测、归档 `1..N` 完整性、REST 跨页缺号判定、batch rank 切片、故障原子性与崩溃恢复语义。若仓库当前 infra API 无法提供有界批次 reader，可在 infrastructure 内扩展，不更改冻结 domain/core 合同。

关闭前必须：

- 加结构断言覆盖所有大型临时量与长期缓存：每次 Arrow 物化行数、解析器留存 rows、positions / seq / time 列表、plan / index / done / commits 容器；测试必须检查深层对象与每个容器的 cardinality，不能只统计每帧的最大局部值。
- 使用固定 microbatch M=256（或更小的实际配置）并覆盖至少 10k、100k、500k 行及足够多 batch 的多组 N；按大小使用隔离子进程。父进程持续采样子进程 `/proc/<pid>/status` 的 RSS 或等效实时驻留指标并记录采样间隔、基线和配置。不可用 `ru_maxrss_after - VmRSS_before` 直接宣称阶段 peak；若用 HWM，必须在测量子进程启动后立刻记录基线并清楚披露它是进程级峰值。定义且记录明确通过阈值：同一 M 时，大 N 的新增峰值不得按 N 或 batch 数线性增长，并与结构上界相互印证。
- 容量探针至少分别测 strict archive verification、normalization/write/recovery；每个规模各用新进程，确保高水位互不污染。探针中的 batch ID / seq 必须从该 fixture 的实际已提交批次读取，不假定首个 seq 对边界输入总是有效。
- 重跑 Canonical 定向测试、相关 PIT / quality 调用方测试及 PostgreSQL normalizer 测试（若 PostgreSQL 测试库可用）；更新本记录和项目状态。
- 不得仅把文档里的容量承诺改成较弱说法来关闭该项。

### 逐条对应（上文 E1-CAP-1 第 1～6 项）

1. 位置：归档单元按固定窄窗逐段证明恰为 `1 … N`，此后为 `range`；REST 单元至多一页。
2. 已提交 `arrival_seq` / `knowledge_time`：块基址与就绪时间取自一条已提交行，其余按整批平铺的窄窗核对（每窗 ≤ `max(narrow_rows, M)` 行 + 1）。
3. 全单元 Python list：`_survey` / `_unit_facts` / `_close` 不再构造全单元序号表；整单元读行只在明确命名的 `collect_unit_rows()`（O(N)，生产路径不调用）。
4. `ParsedArchive.rows` 缓存：改为磁盘 spool（`spool_dir` 须在磁盘；本机 `/tmp` 为 tmpfs），每次证明只读回本窗口的块；缓存 ≤ 2 个 spool，逐出 / `close()` 即删除。
5. plan / index / done / commits：计划为三个整数；D2 行批计划同为三个整数；批次快照从固定历史流式取出；`_write` 从 `count` 续跑；返回值为 `row_count` / `batch_count` / `committed_batches` / `snapshot_id`。
6. 结构测试：见下。

仍随提交数增长、未被本轮消除的：Iceberg 表元数据本身（每个已提交批次一个 snapshot 与一个 manifest），PyIceberg 每次读取与每次提交都加载 / 重写它；这是按 ADR-0028 §6 每批一个快照的存储形状，不是 normalizer 持有的状态。固定常数项：被触及的 D2 行批整批重读（随 D2 自己的批大小，默认 25 000 行）、窄窗（默认 65 536 行）。spool 占用 O(N) 字节磁盘。`check_rest_page` 的 `_KEY_CHUNK` 容量限制（D-33-CAP）未改动，仍为未测 follow-up。

### 结构测试（`tests/infrastructure/canonical/test_normalizer_capacity.py`）

- 固定 M = 4、窄窗 8、D2 行批 4；单元 24 行（6 批）与 96 行（24 批）。对 normalizer / verifier / spool / parser / pinned view 各帧在每次 return 与 yield 时递归审计局部变量与本代码库对象（pins、verifier 缓存、spool、survey、plan、返回值），按路径记录每个容器的最大元素数。

### Codex 根因复核与小规模对照（2026-09-27）

两个独立只读复核都指向 PyIceberg 的重复快照 / manifest 规划，而不是已检查到的 normalizer 跨批 Python 容器：

- `PyIcebergCatalogAdapter.scan_columns()` 每次都 `_require()` 并重新加载表元数据；`PinnedCatalogView` 固定的是 snapshot ID，不复用加载后的表对象。
- 每个批次的 replay 至少调用 `_check_committed_window()` 与 `_check_unique()` 两次 Canonical 限行扫描；resume 的回读也重复扫描。PyIceberg 对每个 scan 仍需从 snapshot 读取 manifest list 并构造规划输入，`limit` 只限制返回行数，不限制扫描规划阶段枚举的 manifest 数量。批次数 H 增长时，这会反复分配与 H 相关的短命元数据结构，并抬高 RSS 高水位。
- normalizer 的 plan / 批次状态容器仍是常数规模；现有结构审计没有发现随批次数保留的 Python list。RSS 无法区分存活对象与 native allocator 高水位，因此上面的归因是源代码支持的强假设，还不是通过逐 scan 计数或 heap profile 证实的测量结论。
- 单纯缓存一份 `IcebergTable` 可以减少 JSON 解析 churn，但不能消除每个批次重复规划完整 manifest 集合，也会改变固定快照期间的元数据保留语义；不能据此宣称容量问题已解决。

作为诊断而非验收，另在修复后以 N = 2,000 / 4,000 / 8,000、M = 256、narrow = 4,096 跑了相同探针。所有阶段的跨规模 delta 增长均 ≤ 15.7 MiB，CLI 报告 `pass: true`；对应批次数仅 8 / 16 / 32，远低于正式覆盖的 10k / 100k / 500k，因此不能推翻 500k 的 resume / replay 失败，也不能作为 E1 容量验收。

下一次修复应先给容量探针增加常数空间的计数器，记录每阶段 `scan_columns` 次数、每次规划枚举的 manifest 数、metadata reload 次数及返回行数，以 10k / 100k / 500k 确认增长来源。之后只在 infrastructure 层优化固定 snapshot 上重复证明的扫描计划，或使用有界内存的外部存储索引 / 流式 reader；必须继续核对每批 fingerprint、逐批 readback、缺行与重复、固定 snapshot、崩溃恢复、时钟读数及外部 head 变化。不得把失败归因到 allocator 后就忽略 RSS，也不得只加表对象缓存或放宽阈值。
